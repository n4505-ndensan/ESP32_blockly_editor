# ADR 0001: 部品の状態表示と操作

- ステータス: 採用
- 日付: 2026-09-14

## 背景

現状、ESP32につないだ部品（LED・ブザー・センサ）を画面から扱う手段は、SSEで流れてくる
温度と距離の数値表示だけだった。配線やセンサの動作確認をするたびにファームウェアを書き換えて
書き込み直す必要があり、プロトタイプの検証速度が落ちている。

そこでまず、BlocklyのASTを実行していない間に各部品を手でON/OFFできるようにしたい。
ただしこれは単独の機能ではない。最終的にASTの実行エンジン（`src/runtime/`）も同じ部品を
動かすため、ここで決めた「部品とは何か」「状態をどう配るか」「操作をどう受けるか」は
そのまま自動制御の土台になる。手動操作用に別経路を作ると、後でAST実行時の状態表示を作るときに
二重実装になり、画面の表示と実機の状態がずれる。

なお、ASTの実行時には部品の初期化が走る想定だが、実行中かどうかのフラグと排他制御は
この段階では導入しない（「将来の拡張点」を参照）。

## 決定

### 1. 部品カタログをファームウェアの単一の定義とする

「どんな部品が存在するか」を`src/devices/devices.cpp`のテーブル1か所で定義し、
`GET /api/devices`で配る。ID・表示名・単位・種別・許される操作・ピン番号・極性をここにまとめる。

画面の操作UIも、将来のBlocklyのツールボックスも、この配信結果から組み立てる。
部品を1つ増やすときにファームウェアのテーブルだけを触れば、操作UIとブロックの両方に反映される。
表示名（`label`）と単位（`unit`）をファームウェア側に持たせるのはこのためで、
「部品の一覧」をフロントエンドにもう1つ書くと、追加のたびに2か所を直すことになる。

### 2. 状態の正はESP32に置き、画面は楽観更新しない

部品の実際の状態を知っているのはESP32だけである。画面はボタンを押した瞬間に表示を
切り替えず、ESP32が返した状態・配信した状態を受け取ってから反映する。

これはAST実行を見据えた判断でもある。AST実行中はプログラムが部品を動かすので、
画面の操作だけを信じると表示と実機が必ずずれる。状態の流れを
「操作 → ESP32が実行 → ESP32が状態を配る → 画面が描く」の一方向に固定しておけば、
変化の発生元（手動・AST・起動時の初期化）が何であっても画面の作りは変わらない。

送信中の部品には「送信中」の印を出し、応答が返るまで操作を受け付けない。

### 3. 操作は冪等な`set`だけにし、`toggle`は持たない

操作は「この部品をONにする / OFFにする」の指定だけとし、「反転する」は用意しない。

反転は現在の状態に依存するため、画面が持っている状態が古いと意図と逆の結果になる。
操作元が画面だけなら実害は小さいが、ASTが同じ部品を動かすようになると、
画面が知らないうちに状態が変わっている状況が普通に起きる。
`set`だけなら再送しても結果が変わらず、通信の取りこぼしを気にせず再試行できる。

### 4. 状態の配信は「変化した部品だけ」をSSEで流す

既存の`/events`をそのまま使い、`devices`という名前のイベントに、
前回の配信以降に変化した部品のIDと状態だけをJSONで載せる。

- SSEに接続した直後は、その接続に対してだけ全部品のスナップショットを1回送る。途中参加でも状態が揃う。
- センサ値は毎回わずかに動くので、部品ごとに変化とみなす幅（`epsilon`）を持たせ、
  ノイズだけで配信が発生しないようにする。
- 配信の間隔は100msを上限とし、この間に複数回変化してもまとめて1回送る。

カタログ（静的な定義）はHTTP、状態（動的な値）はSSEと役割を分ける。
カタログをSSEに載せないので、接続のたびに同じ定義が流れることがない。

### 5. センサも出力部品と同じ名前空間の「部品」として扱う

温度・距離も、LEDやブザーと同じIDの体系に入れ、同じ`devices`イベントで状態を配る。
違いは「許される操作」が`none`か`switch`かだけとする。

ASTでは「距離が200mm未満なら赤色LEDをつける」のように、センサと出力を同じ粒度で参照する。
読み取りと操作でデータの通り道が別々だと、ブロックの生成も実行エンジンも
部品の種類ごとに分岐が増える。入口を1つにしておけば、部品の追加が表の1行で済む。

この結果、従来の`temperature`・`distance`という個別のSSEイベントは廃止する。
配信元が`devices`イベントに一本化されるため、同じ値を2つの形式で流す必要がない。
`data/index.html`（旧デモ）はこの変更で動かなくなるが、配信対象は既に`data/web/`へ移っている。

### 6. 部品の起動時の状態を必ずOFFにそろえる

起動時に全部品を短時間ONにして点灯・鳴動を確認した後、必ず全部OFFにしてから
サーバーを開始する。状態の正をESP32に置く以上、起点の状態が決まっていないと
最初のスナップショットが実機と食い違う。

LEDとブザーはHIGHでONになる配線として扱い、極性が違う部品のために
カタログに`activeLow`を持たせる。

## 通信仕様

### `GET /api/devices` — カタログと現在の状態

```json
{
  "devices": [
    {
      "id": "led_red", "label": "赤色LED", "description": "", "unit": "",
      "kind": "output", "control": "switch",
      "state": { "on": false }
    },
    {
      "id": "temperature", "label": "温度", "description": "検出範囲の最高温度", "unit": "℃",
      "kind": "sensor", "control": "none",
      "state": { "value": 24.5 }
    }
  ]
}
```

- `kind`: `output`（操作できる部品）/ `sensor`（読むだけの部品）
- `control`: `switch`（ON/OFF）/ `none`。将来`level`（PWM）や`tone`（音階）を足す余地を残す
- `state`: `output`は`on`のみ、`sensor`は`value`のみを持つ
- `description`: 画面に出す短い補足。不要なら空文字。部品ごとの説明を画面側に持つと
  部品を足すたびに2か所を直すことになるため、`label`・`unit`と同じくカタログに含める

### `POST /api/devices/command` — 操作

```json
{ "id": "led_red", "action": "set", "on": true }
```

成功時は200で、その部品の確定した状態を返す。

```json
{ "id": "led_red", "state": { "on": true } }
```

失敗時はHTTPステータスと`error`コードを返す。

| 状況 | ステータス | `error` |
| --- | --- | --- |
| JSONが壊れている、`id`が無い、`on`が真偽値でない | 400 | `bad_request` |
| そのIDの部品が無い | 404 | `unknown_device` |
| センサに`set`した、未対応の`action` | 422 | `unsupported_action` |

### SSE `devices`イベント — 状態の配信

```json
{ "ts": 128400, "devices": [{ "id": "led_red", "state": { "on": true } }] }
```

- `ts`はESP32の起動からの経過ミリ秒。順序の確認に使う
- 接続直後のスナップショットも同じ形式で、全部品を載せて送る
- カタログの情報（`label`など）は載せない

## 影響

### 良くなること

- 部品を1つ増やす作業が、ファームウェアのテーブルに1行足すことに集約される
- 手動操作とAST実行で、状態表示のコードを共有できる
- 操作が冪等なので、通信の再試行やクライアントの複数接続を特別扱いしなくてよい

### 引き換えになること

- 画面の反応がESP32の応答を待つぶん、わずかに遅れる（実測で問題になれば配信間隔を詰める）
- 生の数値を流すだけだった頃よりSSEのペイロードが増える。変化した部品だけに絞ることで抑える
- `data/index.html`（旧デモ）は動かなくなる

### 将来の拡張点

ここでは決めず、必要になった時点で別のADRにする。

- **実行中フラグと操作の排他**: AST実行中に手動操作を拒否するか、割り込みを許すか。
  カタログに`busy`のような項目を足すか、`/api/program/state`を別に持つかもそのとき決める。
- **`control`の追加**: `level`（明るさ）、`tone`（ブザーの音階）。`state`に`level`・`frequency`を足す形で拡張する。
- **操作のまとめ送り**: ASTの1ステップで複数の部品を同時に変えたい場合。
  `POST /api/devices/command`が配列も受け取る形にすれば、今の仕様と両立できる。
