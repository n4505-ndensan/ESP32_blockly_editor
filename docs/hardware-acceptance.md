## 発見・修正した試験コードの問題

- SSE再接続試験のGETに`Accept: text/event-stream`がなく404になりました。
  ESPAsyncWebServer 3.12.0はSSEヘッダを使ってルーティングするため、ブラウザEventSourceと同じヘッダへ修正しました。
- 最初の10分継続試験は、無制限HTTPポーリングによりWindows側でWinError 10048（ソケット枯渇）になり中断しました。
  サーバーが応答後にTCP接続を閉じるため、状態取得をシリアルテレメトリの周期（約1Hz）へ制限して再実行しました。
  中断後のSTOPと同一bootIdを確認しており、この失敗をESP32の再起動とは扱っていません。
- 計測用環境の依存取得がHTTPClientErrorで失敗したため、通常環境で取得済みのライブラリキャッシュを再利用しました。

## 停止時間と安定性の測定

`acceptance_test`環境だけで`PROGRAM_DIAGNOSTICS`を有効にします。通常ビルドには計測・ログ出力を含みません。
停止処理入口（mutex取得前）から、loop側の`engine.stop()`による全GPIO OFF処理完了までを`micros()`で測ります。
I2C処理によるloop待ちとmutex待ちを含み、HTTP送受信時間とSSE表示遅延を含みません。
ログ生成はランタイム・部品のロック外です。

| 計測 | 120秒試験 | 600秒試験（約1Hzに修正後） |
| --- | ---: | ---: |
| 開始停止の反復 | 100回 | 200回 |
| ウォームアップ後の停止計測数 | 101 | 201 |
| 起動後の最大停止時間 | 13.583ms | 17.316ms |
| 試験前の静止時ヒープ中央値 | 227,260 bytes | 227,260 bytes |
| 試験後の静止時ヒープ中央値 | 227,260 bytes | 226,804 bytes |
| 差 | 0 bytes | −456 bytes |
| 連続実行中の状態取得 | 3,303回 | 599回 |
| bootIdの変化 | なし | なし |

停止試験はLEDをONにして、長い待機と待機なし空無限ループを交互に実行します。
反復前に10回ウォームアップし、静止時ヒープは通信を行わない5つの周期測定の後半4点の中央値です。
自動判定は「停止100ms以内」「bootId不変」「静止時ヒープ低下4KiB以内」です。
最大停止時間とminHeapは起動からの累積値なので、600秒試験の値には先行試験も含みます。
最終試験で取得した起動後minHeapは142,088 bytes、試験中に観測した最大連続空きブロックの最小値は110,580 bytesでした。
**−456 bytesの差は合格条件内ですが、長期的なリークがないことを証明する結果ではありません。**

生データはGit管理外の`.pio/acceptance-report.json`、`.pio/acceptance-report-10min.json`に保存しています。
中断した試験の記録は`.pio/acceptance-report-long.json`です。

## 再実行方法

Python環境にpyserial、PCにPlatformIOを用意してください。通常ファームウェアの依存ライブラリとLittleFSも必要です。
以下はリポジトリルートで実行します。試験はLED等を操作します。

```sh
pio run -e acceptance_test -t upload --upload-port <COMポート>
python scripts/test_acceptance.py http://<ESP32のIP> --port <COMポート> --duration 600 --cycles 200
pio run -e esp32dev -t upload --upload-port <COMポート>
python scripts/test_program_api.py http://<ESP32のIP>
```

`--duration`と`--cycles`で継続時間・反復回数を変更できます。失敗時もSTOPを試み、結果JSONを保存します。
通信自体が失われた場合、STOP成功は保証できません。実機の出力を確認してください。
Playwrightはfrontendで`VITE_ESP32_TARGET`を設定して`pnpm test:browser`を実行します。
実機対象の各ブラウザ試験にはSTOPと停止状態確認の後処理を追加しています。
